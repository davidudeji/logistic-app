# Build invoices that freeze when sent

Build the module around one rule: a document is a draft you can edit freely until the moment of "Send", and at that moment it becomes a frozen snapshot with a number, a stored PDF and a hash. For PDF generation, start with **@react-pdf/renderer** behind a single `renderInvoicePdf(snapshot)` function, because it needs no browser binary, renders in under 500 ms, and lets the three templates share React primitives and the same components for live preview ([dev.to production comparison](https://dev.to/iurii_rogulia/pdf-generation-on-the-server-puppeteer-vs-react-pdfrenderer-a-production-comparison-44cg)). Move to HTML plus Gotenberg or Chromium only if the designs outgrow flexbox, which is unlikely for tabular invoices. Send email through **Resend** with the stored PDF attached as bytes, from a platform-owned subdomain, with the tenant's name in the display name and the tenant's address in Reply-To. Store money as integer kobo, assign numbers only at finalize inside the same database transaction, and keep VAT, TIN, WHT and e-invoicing fields as first-class data from day one. Most small tenants are unlikely to need NRS e-invoicing before 2028, but a few larger tenants already do. The main things you must verify yourself are Nigerian VAT/WHT treatment of freight, whether your payment cards work with each vendor, and the exact library APIs, since many vendor pages could not be fetched during research.

## React-pdf first, with the renderer hidden behind one function

The deploy target decides the PDF engine, and your notes do not say where the app runs. If it runs on Vercel, react-pdf is the clear pick. Puppeteer with `@sparticuz/chromium` costs roughly **400-600 MB of memory per serverless invocation, 3-6 s cold starts and 2-5 s per PDF**, while react-pdf adds about **2 MB and renders in under 500 ms** ([dev.to comparison](https://dev.to/iurii_rogulia/pdf-generation-on-the-server-puppeteer-vs-react-pdfrenderer-a-production-comparison-44cg)). Those numbers are one author's production anecdotes, not benchmarks, but they match the platform limits: Vercel caps an uncompressed function bundle at **250 MB** and request/response bodies at **4.5 MB** ([Vercel Functions Limits](https://vercel.com/docs/functions/limitations)), and getting Chromium to fit needs a version-matched `chromium-min` pack hosted elsewhere ([Vercel community thread](https://community.vercel.com/t/sparticuz-chromium-min-working-with-vercel-for-pdf/7877)). On a VPS or Docker host, Chromium is viable (ideally through a self-hosted Gotenberg container), but it is more infrastructure than a solo freelancer needs for a first release.

React-pdf's limits are real but mostly irrelevant here. It supports flexbox but not CSS Grid or pseudo-selectors, handles absolute-position overlays poorly, and `renderToBuffer` does not stream. Fonts must be registered once at module load, before the first render, or parallel requests can race. For invoices these constraints cost little: zebra striping is a JS index check, the repeated table header uses the `fixed` prop, and rows use `wrap={false}` so they never split across pages. Design the seam first. The only function the rest of the app calls is `renderInvoicePdf(snapshot): Promise<Uint8Array>`, so swapping in Gotenberg later touches no routes.

Structure the code as a template registry. A template is a pure function of one serialisable `InvoiceDocumentData` object plus brand tokens, keyed `classic@1`, `modern@1`, `minimal@1`. The snapshot stores the exact key, and released versions are never edited: a redesign becomes `@2`, active only for new documents. This follows the guidance that an old document must never be re-rendered with a newer template ([AppMaster](https://appmaster.io/blog/pdf-generation-app-data-documents)). The registry layout and contract below are my design synthesis, not a sourced pattern.

```ts
// src/invoicing/pdf/types.ts
export type InvoiceTemplate = {
  id: 'classic' | 'modern' | 'minimal';
  version: number;
  label: string;
  Component: (p: { d: InvoiceDocumentData; brand: BrandTokens }) => React.ReactElement;
};
// registry.ts: Record<`${id}@${version}`, InvoiceTemplate>
// render.ts:   renderToBuffer(<registry[d.templateKey].Component d={d} brand={brand} />)
```

Draft previews can render on demand, since that is cheap with react-pdf. For live in-editor preview, drive `usePDF` or `pdf().toBlob()` from the same components with a 300-500 ms debounce, so the preview matches the output. Do not maintain an HTML preview plus a separate PDF implementation, because layout drift between the two is the usual failure ([templates notes, Path A vs B](https://dev.to/iurii_rogulia/pdf-generation-on-the-server-puppeteer-vs-react-pdfrenderer-a-production-comparison-44cg)). Whether `usePDF` runs well in your Next.js version is unverified, so test it first. The code sketches in the research were written from memory of the APIs and never executed, so smoke-test them against the versions you install.

## Three templates, one data shape, and a logo pipeline that never trusts uploads

The three templates should differ in tokens and header layout, not in data. They share primitives (header, meta block, line-items table, totals, footer), and each takes a single `accentColor` plus the logo. The content order comes from invoice design guidance: amount due and due date findable within about five seconds, brand colour only on accents, right-aligned tabular figures, and a design that survives grayscale printing ([InvoiceQuickly design guide](https://invoicequickly.com/guides/invoice-design-guide)). Use A4 as the default and make paper size a per-company setting, since Stripe's Letter default elsewhere should not be copied for Nigeria ([Stripe docs](https://docs.stripe.com/invoicing/customize)).

**Classic** is the professional default: logo top-left at 56 px or less, a serif "INVOICE" title with the number beneath it, a thin dark rule, From/Bill To columns, ruled rows using a mid-grey rather than a near-white one, and a Balance Due row with heavy rules. Accent colour appears only on the title, the table underline and the balance label. **Modern** puts an accent band across the top holding the logo and title, an Amount Due card, an accent-filled table header and a filled total row, with text colour chosen by WCAG contrast. Offer a "logo on white chip" option, because dark logos vanish on a dark band. **Minimal** is the compact manifest style: a one-line header, a single-line meta strip (Issued, Due, Terms, Ref), no boxes or zebra, 12 mm margins and 9-9.5 pt body text, aimed at long multi-page jobs. Font pairings I would use are Source Serif 4 with Source Sans 3 for Classic, Plus Jakarta Sans with Inter for Modern, and Inter alone for Minimal. These designs are my proposals, not copied from any source. Invoice Ninja's named designs and live preview dropdown are the closest cited precedent ([Invoice Ninja docs](https://invoice-ninja.readthedocs.io/en/latest/invoice_design.html)).

Every invoice or quote must show the company logo, company name, creation timestamp and due date. Put all four in the meta block, formatted ahead of time into the snapshot. Store timestamps as UTC `timestamptz` and render the creation time in the tenant's timezone (default `Africa/Lagos`) with an explicit label such as "1 Nov 2026, 14:32 WAT". Store `issueDate` and `dueDate` as Postgres `date` columns, not timestamps, to avoid off-by-one bugs at midnight. Overdue means `dueDate` is before today in the tenant timezone and the balance is above zero, and it should be derived rather than stored. For quotes, reuse the same templates with "QUOTATION" in the title, "Valid until" instead of "Due date", no payment block and an accept line.

Treat logo uploads as hostile. Accept PNG, JPEG and WebP at launch, and leave SVG for later: SVG is effectively untrusted code, with XSS, SSRF and XML-bomb risks that ordinary image validators miss ([Safe SVG pipeline](https://shuntksh.pages.dev/blog/202506/safe-svg-pipeline)). The rest of this paragraph is my recommended policy, unsourced. Check magic bytes (with `file-type` or sharp metadata) instead of trusting the extension, cap uploads at 2 MB and 4000 px, reject animated files, then normalise with sharp: apply `rotate()`, strip EXIF, fit within about 800x400, flatten JPEG onto white and output PNG. Store it privately under a content-addressed key such as `logos/{tenantId}/{sha256}.png`, and embed it in the PDF as a Buffer or data URI, never a signed URL that could expire mid-render. Copy the logo bytes or hash into the snapshot at send time so a later rebrand does not alter old invoices. With no logo, draw a monogram (one or two initials on an accent-coloured rounded square) with View and Text, and reuse it in the email. Auto-pick the text colour for contrast and darken the accent when it is used as text on white.

The Naira sign needs special care. React-pdf's default font only covers basic Latin, and the notes state the standard Helvetica and Times fonts lack U+20A6 (this is general knowledge, not fetched), so register TTF files for every template font ([dev.to comparison](https://dev.to/iurii_rogulia/pdf-generation-on-the-server-puppeteer-vs-react-pdfrenderer-a-production-comparison-44cg)). The only direct evidence of a Naira glyph is for Plus Jakarta Sans ([google/fonts issue 6322](https://github.com/google/fonts/issues/6322)). Coverage in Inter, Source Sans 3, Source Serif 4 and the others is **unverified**. Add a CI test that checks `font.hasGlyphForCodePoint(0x20A6)` with fontkit for each embedded file, and fall back to printing "NGN" where the glyph is missing. Also check what `Intl.NumberFormat('en-NG', {style:'currency', currency:'NGN'})` outputs on your Node version, and prefer an explicit `'₦' + formatted number` for non-currency-style output. Use ISO codes for non-NGN documents.

## Email: one provider, DB-first sends, attach the stored bytes

Resend is the best fit for an early-stage Node/TypeScript app. Its official pricing shows a free tier of **3,000 emails/month and 100/day**, Pro at **$20/month for 50k**, and all webhook events on every plan ([Resend pricing](https://resend.com/pricing.md)). A message can be up to **40 MB including attachments**, attachments go as base64 `content` or a remote `path`, and emails with attachments cannot use the batch endpoint ([Resend attachments docs](https://www.resend.com/docs/dashboard/emails/attachments)). Invoice PDFs are small, so size limits do not matter at any provider, even Postmark's 10 MB ([Postmark support](https://postmarkapp.com/support/article/1056-what-are-the-attachment-and-email-size-limits)). The alternatives are Amazon SES at **$0.10 per 1,000** (cheapest, but sandbox exit, SNS plumbing and a card are required; [Carly](https://www.usecarly.com/blog/amazon-ses-pricing/), third-party) and Brevo's free 300/day with a 20 MB cap ([Brevo help](https://help.brevo.com/hc/en-us/articles/4402811730962)). SendGrid ended its free plan in May 2025 ([Twilio changelog](https://www.twilio.com/en-us/changelog/changes-coming-to-sendgrid-s-free-plans)). Hide the provider behind a thin `EmailProvider` interface so SES is a later swap. The free tier's 100/day cap could hurt a multi-tenant app on invoice-run days, so plan to move to Pro early.

Nigeria-specific payment is the one open risk. No source confirms that any of these vendors accepts naira cards, and one source says naira cards are largely restricted for international USD transactions, with developers using virtual dollar cards ([Evertry](https://evertry.co/blog/?p=8473)). Resend's and Brevo's free tiers need no card, but verify Pro billing with a virtual USD card before depending on it.

The sending identity matters more than the vendor. Send from a platform-owned subdomain, for example `invoices@mail.yourapp.com`, with a display name like "Acme Logistics via YourApp" and the tenant's address in `Reply-To`. This is an unsourced design judgment, but it avoids both spoofing a tenant's domain and forcing each tenant through DNS setup. Publish SPF, DKIM and a DMARC record of at least `p=none` from day one, even though the strict bulk-sender rules (Gmail and Yahoo in Feb 2024, Microsoft consumer mailboxes in May 2025) formally start at 5,000 messages a day, and keep complaints under 0.1%, with 0.3% as the hard limit ([Courier](https://www.courier.com/blog/email-sender-requirements); [URIports](https://www.uriports.com/blog/email-authentication-sender-requirements-2025/)). Offer custom tenant sending domains later as an advanced option. Attach the PDF and also include a hosted "View invoice" link as a fallback. No head-to-head data on attachment versus link was found, so this is a judgment call. Attach the exact stored bytes so the customer copy equals the archive copy.

Make the send reliable. First write an `EmailMessage` row with status `queued`, then enqueue a job. The job sends with the idempotency key `invoice-email/{messageId}`, which Resend keeps for 24 hours and rejects with a 409 if the payload differs ([Resend idempotency docs](https://resend.com/docs/dashboard/emails/idempotency-keys.md)). The webhook updates status from `sent`, `delivered`, `bounced` and `complained` events. Webhooks arrive at least once, so dedupe on `data.email_id`, verify the Svix signature on the raw body, and reject timestamps older than 5 minutes ([Hookdeck](https://hookdeck.com/webhooks/platforms/guide-to-resend-webhooks-features-and-best-practices.md)). Treat "opened" as an attribute, not a state, because events arrive out of order and Apple's privacy features inflate opens (the Apple claim is unverified background knowledge). A user pressing "resend" creates a new message ID. For the queue, **pg-boss** fits best because you already run Postgres and it allows transactional enqueue, but the research did not verify queue products, so confirm its current API and limits. The sketch below follows the documented Resend shape. Argument names for `webhooks.verify` and the `replyTo` and `tags` fields come from secondary descriptions or memory, so check them against the installed SDK types.

```ts
const { data, error } = await resend.emails.send({
  from: `${sanitize(tenant.name)} via YourApp <invoices@mail.yourapp.com>`,
  replyTo: tenant.billingEmail,
  to: [msg.toEmail],                       // from the customer record, never from the client request
  subject: `Invoice ${inv.number} from ${sanitize(tenant.name)}`,
  html, text,                              // always send a plain-text part
  attachments: [{ filename: `Invoice-${inv.number}.pdf`, content: storedPdfBuffer }],
}, { idempotencyKey: `invoice-email/${msg.id}` });
```

Guard against abuse: only send to addresses on the tenant's own customer records, strip CR/LF from every header field, escape tenant text in templates, cap sends per tenant per day, and auto-pause a tenant whose bounces or complaints spike, since one bad list damages the shared reputation. Suppress hard-bounced and complained addresses per tenant and show that status in the UI. Subjects should be plain and predictable, such as "Invoice INV-2026-00042 from Acme Logistics, due 15 Dec".

## The data model: drafts are cheap, finalized documents are frozen

Stripe's model is the right simple reference: invoices start as drafts and are editable only in that state, and finalizing assigns the number, makes the properties immutable and creates the PDF link. Stripe also copies customer name, address, tax IDs and similar fields onto the invoice at finalization ([Stripe docs](https://docs.stripe.com/invoicing/integration/workflow-transitions)). Copy that. Keep `Quote` and `Invoice` as separate tables with a shared line shape, which is simpler for a solo developer than one polymorphic table. Every table carries `tenantId`, timestamps are `Timestamptz`, and the unique key `(tenantId, number)` is a backstop. The schema sketch in the research is design judgment rather than verified against Odoo or Invoice Ninja, so treat it as a starting point.

Persist a small status set, `DRAFT | OPEN | PAID | VOID` for invoices, and derive "sent", "viewed", "partially paid" and "overdue" from timestamps and balances. The research schema lists more stored states, but combinations such as viewed plus partially paid plus overdue multiply quickly, and keeping `sentAt`, `firstViewedAt` and `balanceDueMinor` as separate columns avoids that. Quotes keep the explicit lifecycle `DRAFT -> SENT -> ACCEPTED | DECLINED | EXPIRED -> CONVERTED`, with expiry also evaluated lazily on read so a missed cron never shows a stale quote. Email-open "viewed" is a weak signal. Only a click-through on the hosted link counts, because mail scanners prefetch links.

Money is stored as integers. Use `BigInt` or `Int` kobo for `subtotalMinor`, `taxMinor`, `totalMinor` and the per-line amounts. Use `Decimal` for quantity (kg and CBM need decimals) and unit price. Compute everything in one pure `computeTotals()` function using Decimal.js, which Prisma already returns, with round-half-up applied per line. Persist the line and document totals, make `total = sum(lines)`, and never recompute at render. Per-line rounding is my choice, not a Nigerian rule: no source on Nigerian rounding was found, but it matches line-level VAT data. Serialise BigInt and money to JSON as strings. Add property-based tests for `sum(lines) == total` and inclusive/exclusive round trips.

Numbering happens at finalize. Drafts have `number = NULL`. A Postgres SEQUENCE is not transactional and leaves gaps on rollback, so use a counter row, one per tenant, document type and year, incremented inside the same transaction that finalizes the document ([Stripe also assigns numbers at finalization](https://docs.stripe.com/invoicing/integration/workflow-transitions); the SQL is the researcher's pattern, not web-verified).

```sql
INSERT INTO number_sequence (tenant_id, doc_type, scope_key, prefix, next_value)
VALUES ($1, $2, $3, $4, 2)
ON CONFLICT (tenant_id, doc_type, scope_key)
DO UPDATE SET next_value = number_sequence.next_value + 1
RETURNING next_value - 1 AS assigned;   -- run via $queryRaw inside prisma.$transaction
```

The row lock serialises finalizations per tenant and type, which is fine for small logistics firms. Keep that transaction short: it does the numbering, snapshot, due-date computation and status change only. Render the PDF, upload it, and send the email after commit, from the queue. Use formats like `INV-2026-00042` and `QT-2026-00007`, with credit notes on their own `CN-` sequence. Voided numbers are never reused.

The finalize step writes a snapshot. Copy the issuer (legal name, address, TIN, VAT number, logo key and hash, bank details), the customer (name, address, TIN, email), each line's frozen tax rate, the template key and the pre-formatted timestamp strings into JSON columns. Render the PDF from that snapshot, never from live tables. Upload it to private storage under an immutable key, record its SHA-256, the renderer name and version, and mark one document per version as current. The notes suggest R2 or S3 with private buckets and short-lived signed URLs, but R2 Object Lock support is unverified. Re-downloads serve the stored file. The email attaches the same file. Corrections after sending follow Stripe's pattern: use a credit note for amounts, or void and duplicate to change customer details ([Stripe docs](https://docs.stripe.com/invoicing/integration/workflow-transitions)). Allow a void only when nothing has been paid, require a reason, keep the row and number, and never hard-delete a numbered document. A Postgres trigger that blocks updates to finalized rows protects against your own bugs. Quotes can be revised through a `revision` counter until accepted, then locked, and "Convert to invoice" creates a new DRAFT invoice (with its own number only at finalize) by copying lines.

For the create/edit screen, use react-hook-form with Zod and two schemas: a permissive `draftSchema` for autosave and a strict `sendSchema` for the Send action. Layout is the form on the left and the live preview with a template switcher on the right, collapsing to Edit/Preview tabs on mobile. Autosave is debounced at 1-2 seconds, uses a `version` counter to prevent overwrites from another tab, and shows "Saved 14:32" in an `aria-live` region. The send dialog prefills recipients from the customer, a templated subject and message, "send me a copy", Reply-To, and a PDF preview, and it keeps the dialog open with the reason on failure. Provide move up/down buttons beside drag handles for accessibility. The UX patterns here are largely synthesis, because no primary source for QuickBooks, Zoho or Wave could be retrieved.

## Nigerian context: model the tax fields now, defer e-invoicing

VAT is **7.5%** under the reforms effective 1 January 2026, and the planned rise to 15% was dropped. Small businesses with turnover of **NGN 100m or less and fixed assets of NGN 250m or less** (excluding professional services) are exempt from VAT registration and charging ([Forvis Mazars](https://www.forvismazars.com/ng/en/services/tax/nigeria-s-tax-reform-in-focus/2025-nta-vat-key-business-changes)). So add a `vatRegistered` flag on the tenant: unregistered tenants issue invoices with no VAT line. Per-line `taxCategory` (standard, zero-rated, exempt) and a frozen `taxRate` handle everything else. The important unknown is how domestic and international freight is rated. The BusinessDay review says transport operators must file monthly VAT returns by the 21st, but it does not say how freight is rated ([BusinessDay](https://businessday.ng/news/legal-business/article/what-transportation-stakeholders-must-know-a-review-of-the-provisions-of-nigerias-tax-reform-acts-2025/)). Default to a configurable per-line category and get a Nigerian tax adviser to confirm before launch. Mandatory invoice content, per one secondary source, is the supplier's Tax ID, a sequential number, supplier name and address, date of supply (which can differ from the invoice date), customer name, gross amount, and VAT rate and amount ([InvoiceQuickly Nigeria](https://invoicequickly.com/blog/invoice-requirements-nigeria)). Verify that list against NRS guidance, and store TIN, date of supply and tax rate as real fields. Treat TIN as a free-form string: a claim of a new 13-digit Tax ID appears in only one commercial source, so do not hard-validate length.

Withholding tax is deducted by the customer from the payment, so never add it to the invoice total. Under the 2024 regulations, effective 1 January 2025, monthly transactions of NGN 2m or less are exempt if the supplier has a valid TIN, and the rate doubles if the recipient lacks one ([Forvis Mazars](https://www.forvismazars.com/ng/en/services/tax/tax-alerts/2024-wht-regulations-overview)). Rates include 2% for goods and 2% (resident) or 5% (non-resident) for other services, and no haulage-specific rate appears in the source ([Mondaq](https://www.mondaq.com/nigeria/withholding-tax/1491814/an-overview-of-the-nigerian-withholding-tax-regulations-of-2024)). Model it on `Customer.whtApplies`, show an informational "Expected WHT" and "Net payable" on the PDF, and let a recorded payment carry a `whtWithheldMinor` portion so an invoice can settle when cash plus WHT credit equals the total. Which rate applies to haulage is **unverified**.

E-invoicing is the item to size correctly. NRS's phased schedule puts large taxpayers (over NGN 5bn) first, medium taxpayers (NGN 1bn-5bn) at go-live on **1 July 2026** with enforcement from January 2027, and emerging taxpayers (under NGN 1bn) at go-live on **1 July 2027** with enforcement from January 2028 ([Sovos](https://sovos.com/regulatory-updates/vat/nigeria-nrs-publishes-e-invoicing-timeline/); [RegFollower](https://regfollower.com/nigeria-nrs-expands-mandatory-e-invoicing-rollout-to-medium-and-emerging-taxpayers/)). Once a buyer is in scope, a PDF is not the legal document. The cleared invoice carrying an IRN is, and buyers cannot claim input VAT without one ([TechCabal](https://techcabal.com/2026/04/16/all-you-need-to-know-about-e-invoicing-in-nigeria/)). That is also the strongest argument for immutability after sending. Sources conflict on dates: one says small and medium VAT-registered businesses faced a 1 January 2026 deadline ([Kuda](https://business-support.kuda.com/en/articles/13254426-firs-e-invoicing-what-nigerian-businesses-need-to-know)), and the notice date and the large-taxpayer go-live differ across outlets. The practical stance is to add nullable `irn`, `csid`, `qrPayload` and `clearedAt` columns, buyer TIN and per-line tax category now, leave a footer slot for a QR code, and integrate through a certified access-point provider only when a tenant needs it, since businesses do not deal with NRS directly. Do not make any compliance claims in your marketing until you have checked official NRS guidance, which the research could not reach.

## Build in this order

Each step below should ship something usable before the next begins.

| Step | What to build | Why it comes here |
|---|---|---|
| 1 | Prisma schema (Tenant, Customer, Quote, Invoice, DocLine, NumberSequence, EmailMessage, AuditEvent), tenant scoping on every query, and `computeTotals()` with tests | Money and tenant isolation are the hardest things to retrofit |
| 2 | Draft CRUD and the editor with autosave, customer picker, line-item grid and Zod draft/send schemas | Gives you a testable surface with no PDF yet |
| 3 | `renderInvoicePdf` with the Classic template only, registered fonts, the Naira glyph test, and a fixture set (1, 12 and 60 lines, long names, no logo, NGN and USD) | Proves the engine and fonts before multiplying templates |
| 4 | Logo upload pipeline, brand settings, monogram fallback and the snapshot builder | Branding must be in the snapshot before Finalize exists |
| 5 | Finalize transaction (number, snapshot, due date, lock), then post-commit render, upload and SHA-256 | The core of the module |
| 6 | Email: Resend, queue, idempotency key, webhook status, send dialog, suppression and per-tenant caps | Needs the stored PDF from step 5 |
| 7 | Modern and Minimal templates, template switcher, live preview and a grayscale/golden-file test per template | Cheap once the primitives exist |
| 8 | Quote lifecycle, convert to invoice, payments with WHT, derived overdue and reminders | Builds on a stable invoice core |
| 9 | Void, credit notes, public share links, rate limiting, Postgres RLS, and later shipment-to-invoice billing runs and e-invoicing | Hardening and extensions |

Keep the template count at one until step 7. Drafting three templates before the data model and finalize flow are solid is the most likely way to stall.

## Conclusion

The central insight is that the "3 templates with logo, name, timestamp and due date" request is the smallest part of the problem. Once an invoice leaves the building, it is a legal and financial record, so the real design work is the snapshot boundary: what is frozen, when, and who can change it afterward. If you build that boundary first, templates become interchangeable skins, email becomes a delivery of stored bytes, and Nigerian e-invoicing becomes an adapter rather than a rewrite.

Three decisions remain open for you. First, pick the deploy target, because it switches the PDF recommendation between react-pdf and Gotenberg. Second, confirm vendor billing from Nigeria with a virtual USD card before committing to Resend Pro or SES. Third, get a tax adviser to rule on freight VAT and haulage WHT. Everything else in this report is a defensible default that you can test in a week.
